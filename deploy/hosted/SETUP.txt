VitaAi hosted candidate (single container)

This original package prepares a web/API pair for a TLS-terminating host.
It does not publish, provision an identity, or grant provider/write permission.
Build only reviewed source; preserve existing data and unrelated services.

From the repository root:
  docker build -f deploy/hosted/Dockerfile -t vitaai-hosted:candidate .

The default-deny context excludes private Markdown, .env, Git history, databases
and caches. No runtime configuration or secret build arguments are declared.
Versioned base tags are mutable; this is not complete supply-chain certification.
The non-root runtime includes Python and Node; API binds only 127.0.0.1:8000.
Web alone binds 0.0.0.0:PORT (default10000). Fixed Next gateways are unchanged.

Supply runtime configuration through the host's private environment settings:
  AUTH_MODE=session
  SESSION_COOKIE_SECURE=true
  WEB_ORIGIN=https://your-reviewed-service.example
  VITAAI_WEB_ORIGIN=https://your-reviewed-service.example
  DATABASE_URL=<private PostgreSQL connection URL>
  PORT=10000

Origins must be the same exact lowercase HTTPS DNS origin, with no port/path.
PostgreSQL is mandatory: ephemeral SQLite is refused. PostgreSQL URLs are mapped
to the installed psycopg driver, with TLS required unless stronger verification
is explicitly configured. Do not print credentials, commit env files or place
secrets in build arguments. Only the API child receives database/provider secrets.
Keep integration/write/worker gates disabled unless separately authorized.

Startup performs the existing API migrations and missing-only synthetic sample
initialization against the configured database. No default account/password is
created. Review a new database before initialization; never point a test candidate
at another application's database. Provision chosen users through the existing
vita_api.identity CLI from an authorized private environment with a secure prompt.
For that CLI, set DATABASE_URL explicitly to the postgresql+psycopg:// form with
sslmode=require (or stronger verification); URL normalization occurs in the
hosted launcher, not in a separately invoked identity CLI.
The API must pass schema readiness before web starts. Failure or unexpected exit
of either child stops/reaps both; SIGTERM/SIGINT requests graceful pair shutdown.
No automatic child restart or data cleanup occurs.

Render settings, when separately reviewed for deployment:
  Runtime: Docker; repository root context; Dockerfile: deploy/hosted/Dockerfile.
  Use a dedicated reviewed service in the database's region; preserve others.
  Keep auto-deploy off until the exact candidate/source is approved.
  Set HTTP health path /api/auth/session and confirm its actual Host is the
  configured origin's hostname. The container health probe also checks API
  schema readiness. TLS terminates at the platform; do not publish port8000.

For the first initialization of an explicitly reviewed empty dedicated database,
use this one-time Docker Command instead of an inline Python command:
  python /opt/vitaai/deploy/hosted/preflight.py
It validates the same configuration, inspects visible non-system tables in a
read-only transaction, and launches only when that count is zero. Failure or a
nonzero count stops without migration or cleanup. This is not a full pristine
database audit. Remove the override after first successful startup and before
any restart/redeploy; the normal Dockerfile command preserves existing data.
It creates no identity and prints no credentials.

The explicit deploy/hosted/render.yaml Blueprint targets the existing reviewed
vitaai-stage6 service only. Use existingResources=adopt and autoSync=false;
inspect the plan for that exact service before approval. It defines no database,
secret or environment variable; existing private environment values are retained.
After first successful initialization, change its dockerCommand to
  python /opt/vitaai/deploy/hosted/launch.py
and review/sync that correction before restart. Future Blueprint syncs remain
manual; do not apply the empty-database command to an initialized database.

Render Free has ephemeral files, idle spin-down and no shell/one-off jobs. Use
an authorized external PostgreSQL CLI environment for explicit provisioning.
Free PostgreSQL expires30days after creation; it does not establish durable
release/judging availability. Never upgrade or create replacement resources
without authority. Cold-start, resource limits, TLS, session/restart storage,
browser/provider/OAuth and release acceptance require actual measured evidence.
Local tests or an image build alone establish none of those external claims.

PostgreSQL backup and recovery rehearsal

Run these steps from an authorized operator environment. Use the PostgreSQL
client for the source server's major version. Configure separate libpq service
entries named vitaai_backup and vitaai_restore with the approved connection and
TLS settings. Obtain credentials through the operator's secret store and keep
them out of commands, logs and artifacts. Work in a new directory in encrypted,
access-controlled storage. Record the source database, backup time, schema head
and application revision in the private recovery record.

  pg_dump --dbname=service=vitaai_backup --format=custom --file=vitaai-recovery.dump
  pg_restore --list vitaai-recovery.dump

Record the archive's byte count and SHA-256. Check the digest again before
restoring. Confirm the restore service points to a separate, empty database on
an isolated network. Keep the source and its running service intact.

  pg_restore --dbname=service=vitaai_restore --single-transaction --no-owner --no-privileges vitaai-recovery.dump

This procedure restores one database. Recreate and review the destination's
roles, ownership and grants separately. Compare the restored schema, including
constraints and migration head, with the source and verify counts and contents
against the same recovery point. Include users, sessions, approvals, audits and
receipts when the source has those records. Record the actual recovery point,
elapsed restore time and any data omitted from the rehearsal.

Start the exact candidate image against the restored database, with provider
writes and workers disabled. Verify API schema readiness, web startup and
authorized sign-in. Reopen retained workflow and assurance records and confirm
session and audit readback across an application restart. Use an approved HTTPS
endpoint to verify browser access and cookie behavior before any cutover.

During a database outage the private API's /health/live can return 200 while
/health/ready returns 503. Alert on readiness failure and keep write traffic
paused during recovery. After database recovery, verify readiness, session
access and protected record readback before resuming write traffic.

Require explicit cutover approval. Account for writes after the backup by
quiescing writes for a final backup or reconciling later changes before moving
traffic. Preserve the prior service and database as recovery options. Verify
schema compatibility before moving traffic back to an older application image.
Before switching back to the prior database, pause writes and reconcile changes
committed to the new database since cutover. Use forward recovery if schema
compatibility or reconciliation cannot be verified.
